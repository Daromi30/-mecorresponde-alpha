## Contrato implementado ahora

- Las claves admiten solo el patrón content-addressed `originals/<case_id>/<sha[:2]>/<sha>`; se rechazan traversal y hashes que no correspondan a los bytes. `put_bytes` devuelve `PutResult(created=...)` para distinguir creación física de objeto idéntico preexistente. Local usa archivo temporal y enlace exclusivo; nunca sustituye una clave ocupada. S3 usa HEAD/GET para acreditar bytes y metadata SHA cuando existe, y PUT condicional `If-None-Match: *`; si un backend compatible no soporta la condición, falla cerrado en vez de degradar a overwrite. Una colisión concurrente se vuelve a leer/verificar antes de tratarla como idempotente. La compatibilidad concreta de cualquier proveedor futuro necesita una prueba de aceptación con ese proveedor, no se presume por la API genérica.
- La subida del mismo contenido/caso devuelve el mismo documento ya persistido tras verificar el objeto, sin segunda extracción/audit ni consumo adicional de cuota. Un bloqueo por clave abarca creación, SQL commit, rollback y compensación. En PostgreSQL es advisory lock de sesión compartido entre workers; en SQLite de pruebas/local es un mutex de proceso. Si se creó un objeto nuevo y falla flush, extracción SQL, auditoría o commit, se revierte SQL, se consulta una referencia confirmada y solo entonces se intenta borrar ese objeto. Un objeto preexistente o ya referenciado nunca se borra por esa compensación. Si el delete compensatorio falla, se emite error explícito y un registro técnico con backend/tipo de excepción, sin bytes, filename ni contenido. Se necesitará un reconciliador de huérfanos antes de datos reales, especialmente para resultados de PUT ambiguos por pérdida de respuesta de red.
- `validate_document_bytes` devuelve MIME canónico para PDF, JPEG, PNG, WebP, TXT y CSV. Exige extensión admitida, MIME declarado concordante (o `application/octet-stream`/ausente), firma binaria simple para los formatos binarios y UTF-8/control básico para texto. `Document.mime_type` y el extractor usan el valor validado, no el header del cliente. Estas firmas **no** son análisis antivirus ni prueba de que un archivo sea inocuo.
- `read_verified_document` lee una sola vez y exige `SHA256(bytes)==Document.sha256` antes de entregar bytes a un consumidor. No existe actualmente un endpoint de descarga ni una ruta de reprocesamiento que lea objetos; la subida extrae de los bytes ya validados de la request. Toda lectura futura de contenido documental debe pasar por esta función. La respuesta de exportación actual es estructurada y no incluye bytes de archivos.
- `DOCUMENT_UPLOADED` conserva solo document ID, SHA-256, backend, declaración de persistencia, estado y tamaño. No duplica raw text, extractos, importes, filename ni `storage_key` en `AuditEvent`. La extracción local permanece en `DocumentExtraction`/`Evidence` según el modelo vigente. Una excepción del extractor genera documento `FAILED` y extracción vacía/flag de error, con objeto y SQL confirmados juntos; una excepción SQL posterior compensa el objeto nuevo.
- Los borrados de caso/cuenta ahora ejecutan y hacen `flush` del borrado SQL antes de tocar objetos; un fallo de SQL en esa fase no elimina bytes. `delete_bytes` sigue idempotente. Un fallo de eliminación física revierte la transacción y no se anuncia borrado exitoso. **Límite cross-resource:** un fallo de commit posterior a la eliminación física, o un fallo a mitad de varios deletes, todavía puede dejar referencias SQL restauradas sin bytes; no existe transacción atómica entre PostgreSQL y S3. Resolverlo requerirá un protocolo de tombstone/outbox o cuarentena/reconciliación antes de datos reales. No se presenta el lifecycle como totalmente atómico.
- En Render, `local` se considera no durable y uploads quedan bloqueados incluso si `document_storage_persistent=true`; ese flag por sí solo no acredita persistencia física. S3 exige bucket, región o endpoint HTTPS coherente, credenciales y prefijo seguro antes de construir cliente, sin incluir secretos en errores. La configuración LIVE continúa local/no persistente: uploads OFF.
