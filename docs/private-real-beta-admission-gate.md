# Private real-beta admission gate (not a launch approval)

This change adds a distinct server-owned `Case.mode`: existing and public `/api/cases` cases are `SYNTHETIC`; only authenticated `/api/real-beta/cases` can create `PRIVATE_REAL_BETA`. The public endpoint rejects a client-supplied mode. This is a provenance/authorization marker, **not** a classifier of the text a person typed. The public synthetic form remains able to receive arbitrary free text, so it must not be represented as safe for real-person data. Real-beta launch remains blocked until that boundary is addressed and independently reviewed.

RB-022 replaces the historical hardcoded interlock with a closed-by-default release gate. Effective opening requires the separate literal `REAL_BETA_ENABLED=true` switch, an exact `REAL_BETA_ALLOWLIST`, one valid versioned release, an exact cohort, and active approvals from separate `OWNER_APPROVER` and `PROFESSIONAL_APPROVER` authorities for the same scope fingerprint. Ordinary operators cannot create or revoke these authorities through the application. No authority, approval or release is seeded; no Render setting is changed by this code. The existing PostgreSQL, privacy-information, transactional-email and persistent-storage prerequisites still apply. A feature deployment, account, reviewer or invitation alone cannot open the gate. This is an internal project control, not a statement of general legal requirements. Do not test with real data.

Only an individually authenticated backoffice operator may issue or revoke a short-lived invitation. Issuance requires a target account already named in the release cohort; the token is bound to that account and release. It returns a 256-bit random secret once and stores only its digest. A signed-in target can accept it while the release remains eligible and the daily admission quota has room. A PostgreSQL lock on the release row serializes quota checks. The shared bootstrap admin token cannot issue invitations. No delivery system is added.

Private case creation requires a current release-bound admission and a family in its exact scope. The release row also serializes the total-case and active-case-per-user quota checks. Owner reads and exports remain available after closure for continuity and rights handling, but writes stop. Participant-facing actionable outputs, including previously approved ones, recheck the current release, authorities, cohort and admission; closing or revoking the release makes them unavailable. Existing human-review rules continue to apply separately. Account deletion remains the existing explicit rights workflow.

Release and authority records require a future, separately controlled out-of-band provisioning and approval process; ordinary application routes do not grant that power. RB-022 does not supply or assert a real professional approval. The public synthetic boundary and external operational, privacy and professional gates remain separate. `REAL BETA READINESS: NOT READY`.
