# Private real-beta admission gate (not a launch approval)

This change adds a distinct server-owned `Case.mode`: existing and public `/api/cases` cases are `SYNTHETIC`; only authenticated `/api/real-beta/cases` can create `PRIVATE_REAL_BETA`. The public endpoint rejects a client-supplied mode. This is a provenance/authorization marker, **not** a classifier of the text a person typed. The public synthetic form remains able to receive arbitrary free text, so it must not be represented as safe for real-person data. Real-beta launch remains blocked until that boundary is addressed and independently reviewed.

The private gate is closed in three layers: `REAL_BETA_ENABLED` defaults to `false` and only literal `true` is accepted; `REAL_BETA_ALLOWLIST` defaults to empty and every code must match the family manifest; and the in-code `REAL_BETA_LAUNCH_REVIEW_COMPLETE = False` interlock cannot be changed by deployment configuration. The technical check also requires PostgreSQL, ready privacy information, operational transactional email, and persistent storage. No Render values are changed here. Removing the interlock is **not** an operational switch: it requires a separate reviewed engineering block, including the public-intake boundary, individual backoffice identity, legal/privacy/risk review, durable database recovery, persistent document storage, and recovery/email model. Do not test with real data.

An administrator using the existing backoffice token can issue a short-lived invitation at `POST /api/admin/real-beta/invitations` and revoke it at `POST /api/admin/real-beta/invitations/{id}/revoke`. Issuance returns a 256-bit random secret once; only SHA-256 is stored. There is no delivery system. A signed-in account can attempt `POST /api/real-beta/invitations/accept`; the conditional update permits one accepted account while the invitation is unexpired and unrevoked. Subsequent status responses do not expose the secret. Failures use a non-enumerating response and audits use internal IDs and normalized reasons only. Existing admin-token identity is shared; this is not an individual reviewer audit trail.

Private case creation requires a current admission and an allowed *classified* family. Rejected classifications roll back the raw intake. Owner session, not an anonymous case capability, is required for private case reads and writes. Writes recheck the switch, allowlist, invitation status and expiration; admin mutations of such cases do the same. If a registered Motor reclassification would leave the allowlist, the case stays in its original family, becomes `HUMAN_REVIEW`, and has no current material decision. The historical source decision remains preserved for review, not a new authorized real-beta conclusion. Revocation or expiry does not delete the dossier: owner reads/exports remain available for continuity and rights handling; new work is blocked pending an operational protocol. Account deletion remains the existing explicit rights workflow.

Threat boundaries: the invitation secret has 256 bits of entropy and its digest is never returned after issue; the database conditional update prevents two accounts binding one invitation. The existing strict same-site session cookie and Origin/Sec-Fetch-Site middleware apply to the new endpoints. The new endpoints are `no-store` and API responses are `noindex`. A leaked existing admin token, the public synthetic free-text path, individual backoffice attribution, concurrent denial-event deduplication, and the external operational/legal gates remain unresolved. `REAL BETA READINESS: NOT READY`.
